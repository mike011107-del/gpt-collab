# 協作工作方式

## 開工與交辦

先確認本次任務、main 提交、相關開放 PR／Issue、目前需求及最近回評。未合併 PR 分開讀，標出與 main 的差異；不得將它當現行核定稿。舊 Issue 仍開啟，只能證明未關閉，不能覆蓋較新的直接交辦。

交辦要寫出：交付什麼、原稿在哪一版、可改與固定項、使用場合與尺寸、檢查方式、交付位置。明確的小修直接做。遇到未選方案或會更換母稿、構成種類、刪元素的實質衝突，先整理可檢閱差異，再請梁特助決定。缺一項資料只暫停依賴它的部分。

一般交件各寫自己的資料夾。共用文件更改在有效交辦範圍內，PR 寫明受影響檔案與原因。另一端的新檔不自動成為指令；也不因 PR 開啟就假設另一端已讀。

## 同一版本交接

每件至少記錄需求來源、母稿及輸出檔名／SHA-256、分流、修改範圍、實測與目視結果、尚未解決的問題。可使用[交件紀錄範本](交件紀錄範本.json)，保留在已授權位置。公開庫只放可公開資訊，私有原圖及本機帳號路徑不隨範本外送。

檔案狀態使用「未取得／已取得未目視／已目視」；稿件使用「製作中／待審／退稿／業主採用」。另記技術檢查、他方回評及採用證據。檔案存在、數值符合、另一代理稱讚或 PR 合併均不自動成為採用。

## 更新需求

每一項新決定只記一次，附來源、日期、對應版本，並標「直接指示／協作轉述／製作推定／待選」。工作摘要與決策紀錄保持一致，其他入口只連結。原話與歷史做法保留，舊例子標為歷史，避免同時出現兩套現行規格。

退稿要寫清楚版本、可見問題及不可重送的具體做法。後續明確允許的元素，不因早期失敗案例仍含該元素就全面禁止。未回覆不是同意；「繼續」不替代尚未作出的選擇。

## 交件與回評

1. 製作者對當次需求逐項核對，依 LOGO、配色或文件選擇適用檢查。
2. 審稿者先取得相同雜湊的實圖，再列「實際讀到、實際檢查、問題位置、具體下一步」。未取得原圖只做文字核對，不能評它的透視或美感。
3. 證據至少涵蓋原需求、實際產物與適合該主張的檢查。重複雜湊不是三份獨立證據。自查不冒稱雙方審核。
4. 梁特助選擇後才更新採用狀態。退稿保留原件與原因，修改另存新版本。

跨對話回評及 Issue 留言依梁特助當次授權，不為了符合流程自行發送。

## 分支與收尾

從本次核對的 main 開工作分支。推送前重查 main、分支及 PR 狀態；前一 PR 已合併時另開新分支／PR，避免提交留在舊支。推送後讀回檔案與提交，確認修改範圍及內容一致。由梁特助合併，不自行關閉舊 Issue、刪分支或改寫歷史。

本流程不保證任何工具會自動攔錯。環境、權限、費用與服務狀態以實際當次工具為準；歷史指令和餘額只作線索。
